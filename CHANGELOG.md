# next version

- Load the product exports of a sales channel again, for example in extensions that read `sales_channel.productExports`. These requests failed with `FRAMEWORK__DEFINITION_NOT_FOUND`, because the extension registered its product export definition a second time.
- When leaving an agentic file, return to the _Agentic Commerce_ tab if it is available. Otherwise, return to the _Agentic files_ tab, which shows again for sales channels and users without the _Agentic Commerce_ tab.
- Show UCP settings as read-only to viewers, let UCP editors save without sales-channel edit access, and require UCP view access for Agentic Commerce Insights.
- Preserve the core save flow for sales channels: required fields are validated for all sales channels, and Storefront theme assignment runs for ordinary Storefront channels.
- Keep disabled agentic files disabled when activating UCP, saving UCP settings, or updating the extension.
  Existing custom content is preserved, and missing default files are created.
- Serve `robots.txt` again on Shopware `6.7.1.0` to `6.7.4.x` instead of answering `500`.
- Mark a missing required feed setting, such as the return policy URL, every time _Save_ is clicked on an Agentic Commerce sales channel, and say so in a message. On an existing channel the message names the _General_ tab, since _Save_ also works from the other tabs, and the field stays marked when that tab is opened. On Shopware `6.5` the save was refused without marking the field or showing a message, so _Save_ looked broken. On a new channel on `6.5` and `6.6`, the second click saved the channel anyway, without the missing setting. Clearing the stored return policy URL is now refused and marked the same way. On `6.5` and on `6.6` before `6.6.9.0` the cleared field kept the stored URL, so _Save_ went through and the old URL reappeared.
- Apply a sales channel's own UCP settings to requests under a domain with a path, such as `https://shop.example/de`. These requests used the UCP settings of the host's root domain. Under the `strict` signature policy, correctly signed requests to such a domain are no longer refused. Agents only discover a UCP profile at `/.well-known/ucp` on the root of a domain, so a sales channel that agents should find needs a domain without a path. A domain with a path no longer serves a UCP profile, and its storefront pages and discovery files no longer link one. Until now `/de/.well-known/ucp` served the profile of the host's root domain. `ucp:config:validate` now warns about a UCP sales channel whose domains all have a path.
- Link the shop's terms and conditions, privacy, revocation and shipping and payment information pages in every UCP checkout response, as `terms_of_service`, `privacy_policy`, `refund_policy` and `shipping_policy` in `links`. Until now an agent got at most the `continue` link and had no legal pages to show the buyer. The links open the pages set under _Settings > Basic information_ for the sales channel, on the domain the agent uses. They carry no `title`, so the agent labels them in the buyer's language. A page that is not set gets no link, and a headless sales channel gets none.
- Accept every agent platform with a valid profile on sales channels that are set up for UCP from now on, as the UCP specification describes. The _Exposure_ sub-tab of the Agentic Commerce tab has a new setting _Who may buy through UCP_ with the options _All platforms_ and _Listed platforms only_, and an _Allowed agent platforms_ field for the list. Until now a sales channel only accepted the platforms on its allowlist, and the list could only be set with `bin/console ucp:config:set`, which merchants in Shopware SaaS cannot run. After switching UCP on in the Administration, an agent whose profile is hosted outside the shop, such as `https://platform.example/.well-known/ucp`, was refused with `401` and "Platform profile host is not allowed by the current runtime configuration". Sales channels that already have UCP settings stay on _Listed platforms only_, so the update opens none of them. The field accepts a host name or a pasted profile URL and stores the host. Under _All platforms_ the field is named _Pre-approved agent platforms_: the platforms listed there never have to wait behind the limits for unknown platforms. On the console the setting is `ucp:config:set --platform-policy=all|listed`. An agent allowlist set with `ucp:config:set` still applies under both options.
- Require the UCP SDK `0.0.10`. It brings the _All platforms_ option and limits how often the shop fetches the profiles of unknown platforms: 60 fetches per minute for all of them together, and a growing pause after a failed fetch. A platform that has to wait gets `503` with `Retry-After`. Profile, key directory and webhook URLs that resolve to a special-use address, such as `100.64.0.0/10`, are now refused, also for listed platforms. A2A requests are now checked like REST requests. A call without a `UCP-Agent` header, or from a platform the sales channel does not accept, is refused with `422` or `401`.
- Refuse a UCP checkout completion unless it carries exactly one payment instrument that names a payment handler listed in `payment_handlers` of the sales channel's profile. A refused completion is answered with `200`, the checkout keeps the status it has with a recoverable `payment_failed` error, and no order is placed. Until now the order was placed with the sales channel's default payment method, also when the instrument named a handler that is not available, for example because its plugin was deactivated. The dry run of the `complete_checkout` MCP tool reports the same refusal. Extensions that call `completeCheckout()` of the checkout adapter are refused as well, because that call carries no instrument.
- Ship the UCP SDK inside the archive again, so that installing or updating the extension no longer runs Composer in the shop. 1.4.0 had Shopware run `composer require` on install and update. On a shop whose packages were older than the newest versions Shopware allows, that updated Symfony and other packages under the running request, and the shop answered `500`. The extension now changes nothing in the shop's `composer.json` or `composer.lock` and needs no access to Packagist. It always uses the SDK it brings, also when the shop's own `vendor/` holds another copy, so a cluster setup that added the SDK to its project for 1.4.0 keeps working. The README section _Updating from 1.4.0 or older_ lists what to expect on that update.
- Remove the requirement on `shopware/agentic-commerce` that 1.4.0 added to the shop's `composer.json`, when updating on Shopware versions before `6.6.10.4`. Shopware removes it itself from `6.6.10.4` on. While it stays, the next Composer run in the shop fails. On a cluster setup nothing changes the shop's `composer.json`, and the extension writes the command that removes it to `var/log/swag-agentic-commerce.log`.
- Load every class of the extension before Shopware replaces its files during an update, so the request that extracts a later version does not run a mix of old and new code.
- List the shop's payment handlers under `payment_handlers` in the UCP profile of every sales channel with UCP switched on. Until now the profile listed them only when `payment_tokenization` was enabled, which the Administration shows as not yet available. An agent found no handler to name in its payment instrument. The extension now brings one handler each for invoice, prepayment and cash on delivery: `com.shopware.invoice`, `com.shopware.prepayment` and `com.shopware.cash_on_delivery`. A sales channel lists such a handler when an active payment method of that kind is assigned to it. The shop picks that payment method itself and ignores a payment method that the agent names. A sales channel also lists the handlers that payment extensions register.
- Run Shopware's payment handling when an agent completes a UCP checkout. This is the step a headless storefront triggers with `/store-api/handle-payment` after placing an order. Until now the order was placed and answered as `completed` without a payment handler running. A payment that needs no redirect answers `completed`. A payment that needs the buyer answers `requires_escalation` with the payment page as `continue_url`, and the checkout reads `completed` once the buyer has paid. A failed payment answers `incomplete` with a recoverable `payment_failed` error. On Shopware `6.5` and `6.6` a failed payment of a prepared payment handler cannot be repeated, so it answers an unrecoverable `payment_failed` error. The order is kept, and completing the checkout again pays this order instead of placing a second one. Cancel Checkout is refused once the order is placed. The agent can also update the checkout with another payment instrument first, which answers `ready_for_complete`, and then complete it. On newer Shopware versions, from `6.6.10.21` and `6.7.13.0` on, this needs _Allow payment change after checkout_ on the payment method. Without it Update Checkout and the second attempt refuse that payment method with a recoverable `payment_failed` error, and the agent can pay with another payment handler. The payment handler of the order's payment method receives the agent's payment instrument under the request key `ucpPaymentInstrument`, so a payment extension can charge the agent's token. The order gets the payment method of the handler the agent names, never the sales channel's default payment method. A handler without a payment method the buyer may use is refused with a recoverable `payment_failed` error, and no order is placed.
- Switch the payment method of a UCP checkout as soon as the agent sends a payment instrument with Create Checkout or Update Checkout. The totals the agent shows the buyer then include a surcharge or a discount of that payment method. A completion whose payment instrument would change the total is refused with a recoverable `payment_failed` error, and no order is placed. The agent then updates the checkout with that payment instrument first.
- Run `AbstractCompletionPaymentApplier::apply()` on Create Checkout and Update Checkout too, with the payment instrument the agent sends, as well as when a checkout is completed. An applier that refuses throws `Ucp\Sdk\Exception\ValidationException`, and the agent gets a recoverable `payment_failed` error with the message of the exception, on creating, updating and completing a checkout. The totals of a created or updated checkout follow the context that `apply()` returns, so an applier returns the context it switched to.

# 1.4.0

- Show the UCP tools only to AI agents that connect through `/ucp/mcp`, instead of to every client of Shopware's own MCP server at `/store-api/_mcp`. 1.3.0 put them into the group Shopware reserves for its own discovery tools, so every client connecting to `/store-api/_mcp` saw the thirteen UCP tools next to Shopware's instruction that no tools are listed until a toolset is enabled -- and models followed that instruction, enabling toolsets for tools they already had. The tools now form their own `ucp` toolset, and `/ucp/mcp` selects it at connect time, so a UCP agent still finds them on its first tool listing while a plain `/store-api/_mcp` connection lists only Shopware's discovery tools. On Shopware versions before `6.7.15.0`, which cannot select a toolset at connect time, the tools stay listed on every connection as before.
- Link the UCP settings to their documentation. The Exposure sub-tab of the Agentic Commerce tab now carries a link below the capability and transport checkboxes that opens the UCP section of the user documentation in a new tab, in the language of the administration. Until now the tab explained each option only in a one-line tooltip and gave no way to read on.
- Keep the settings that other extensions add to the _General_ tab of a sales channel. The extension replaced the tab's content as a whole, so an extension that passes its own data to the tab lost it, and the tab showed the default settings of a storefront sales channel instead.
- Let an extension register its own UCP OAuth scope. The supported scopes were a private class constant, so a plugin that adds a UCP capability of its own had no way to make its scope grantable: the token request threw `Unsupported OAuth scope`, and a consent flow that swallowed the error had already used up its one-time link and told the buyer the link had expired. Tag a scope provider with `swag_agentic_commerce.ucp.oauth_scope_provider` and its scope is advertised in `scopes_supported` on `/.well-known/oauth-authorization-server` and accepted in an authorization request. A request that omits the scope still gets only the three built-in ones; an extension scope has to be asked for by name. An unregistered scope is still rejected -- now with the supported set named in the message, which is what made this hard to diagnose.
- Require Shopware `6.5.8` or newer. `6.5.0.0` through `6.5.7.4` were listed as compatible but could never install: those versions ship Symfony 6.3, while both the extension's own routes and the UCP SDK need Symfony 6.4. Installation therefore ended in a Composer error about `symfony/config` that a merchant cannot act on. Such a shop now sees the extension as incompatible; updating to `6.5.8.x` fixes that and stays inside the same minor.
- Let Shopware install the UCP SDK instead of shipping it inside the archive. 1.3.0 put the SDK in the plugin's own `vendor/` and loaded the autoloader Composer had generated for it, because Shopware does not load a plugin's `vendor/autoload.php` by itself. Every shop that installed it then carried two separate package registries: FroshTools reported `2 autoloaders registered`, and a question as ordinary as which version of a package is installed could be answered from the plugin's copy instead of the shop's. The extension now carries no dependencies at all. It has Shopware run `composer require` on install and update instead, which is what that mechanism is there for on a zip-installed extension: the extension itself resolves from the `custom/plugins/*` path repository every Shopware project declares, and the SDK version it names comes from Packagist into the shop's own `vendor/`. Nothing changes for a shop that installs through Composer. What is new is that the shop needs to reach Packagist (`packagist.org`) while installing or updating the extension -- without it the install stops with a Composer error, rather than leaving an extension that cannot run.
- Switch the extension off instead of taking the shop down when the SDK is missing. An update extracts the new files one request before Shopware runs Composer, so an active extension boots at least once without the dependency it needs. On 1.3.0 every page answered `500` from that moment on, the storefront included, until someone installed the SDK by hand. The extension now registers no services, routes or feeds in that state, and writes to `var/log/swag-agentic-commerce.log` what is missing and the command that fixes it. Once the SDK is there it picks up again on its own. The check asks not only whether an SDK is present but whether it is the version this release names, so a shop still holding the previous one waits instead of running new code against an old SDK. The README has a _Troubleshooting_ section covering what that state looks like, how to leave it, and what to expect when updating from 1.3.0 or older. A cluster setup is the exception: Shopware never runs Composer for a plugin there, so nothing would ever install the requirements, and the extension refuses the install rather than reporting success and then doing nothing.

# 1.3.0

- Register the billing and shipping address the agent actually stated. One address was resolved from the fulfillment destination and registered as the billing address, with no shipping address passed at all -- so an agent that stated the two separately had the parcel sent to the billing address, and a digital cart, which has no destination to offer, had no address at all and could not complete. Billing now comes from `payment.instruments[].billing_address` and shipping from the fulfillment destination, each falling back to the other, and a shipping address reaches Shopware only when it differs from billing.
- Answer the catalog with products an agent can actually buy. Browsing returned the parent of every variant product -- which is not purchasable, so a cart built from it silently stayed empty -- plus one row per variant, all wearing the parent's name. Browsing now returns one row per variant group and no parents, variant titles carry the options that tell them apart (`Acoustic Guitar (Color: Yellow, Material: Spruce Top)`), and `catalog.lookup` and `catalog.product` answer a parent id with a purchasable variant chosen the same way every time. `catalog.product` previously picked a different variant on every call.
- Refuse a line item that never reached the cart instead of reporting success. Shopware drops a product it cannot resolve without leaving an error, so asking for an unbuyable product returned `201 Created`, `status: success`, no messages and an empty cart. The request is now answered with `422` and a recoverable error naming the id, and for the parent of a variant product it lists the variant ids to buy instead.
- Answer a UCP catalog search with an empty query by listing the catalog instead of returning no products. `query` is optional free text in the specification, and an agent opening with a blank search was being told the shop had nothing to sell.
- Answer a UCP request for a cart nobody created with `not_found` instead of handing out a fresh empty cart under the guessed id. Cart ids handed out by `cart.create` are remembered in the same context store the checkout session already uses.
- Name the UCP MCP tools as the specification's OpenRPC document does (`search_catalog`, `create_cart`, `create_checkout`, `complete_checkout`, `get_order` and so on) and advertise them on a fresh MCP session. They were named `shopware-ucp-*` and hidden behind a toolset an agent had to enable first, so a spec-following agent listing tools on `/ucp/mcp` saw only the toolset meta-tools. An MCP client that called the old names has to switch; the arguments are unchanged.
- Return real product descriptions from catalog search and lookup, with the product title as the fallback for a product that has none.
- Hand the payment an agent sends with `checkout.complete` to an extension point that a payment extension can implement. By default nothing changes for the order: it is still charged with the sales channel's default payment method, and the shop log now warns which payment method the agent asked for.
- List the discounts applied to a cart one by one under `discounts.applied`, with code, name and amount, instead of only a total.
- Load agent profiles only from the hosts on the configured allowlist, and keep the secret address of the embedded checkout page from reaching other websites when the buyer clicks through from it.
- Completing an agentic checkout keeps working on upcoming Shopware versions. Creating the guest customer during completion gives the buyer a new Shopware session, and the order is now placed in that new session instead of the old one, which newer Shopware versions reject with a "cart not found" error.
- Product links in the OpenAI and Google product feeds now resolve correctly for headless sales channels on Shopware 6.7.14 and newer, so agents receive working product URLs; the feeds keep working unchanged on earlier Shopware versions.
- Restrict UCP to the sales channels that can actually complete a purchase: Storefront and Headless. Product feed channels are no longer offered for UCP and can no longer have it switched on through the API or the console; one that had it switched on before is now treated as switched off, so no shop is advertised that an agent cannot buy from.
- Serve `/.well-known/api-catalog` (RFC 9727 linkset) on sales channels exposed to UCP, so an agent can discover the shop's UCP profile and Store API entry point from one standardised location; other channels return `404`.
- Add `ucp:setup`, which configures a sales channel for UCP in one step: exposure, security defaults, a signing key when the channel has none, the readiness checks and the first request to run. `--dev` picks local defaults so the shop can act as its own agent; without it the defaults are production ones. The README now walks through the whole setup in four steps.
- Count which UCP versions agents actually speak: one `info` record per request on the new `ucp_negotiation` log channel with the agent's declared version, the served version, the outcome and the agent profile host, nothing else. These numbers decide whether the plugin should one day serve more than one UCP version at a time; SDK `0.0.7` reports them.
- Serve version `2026-08-25` of the UCP specification through SDK `0.0.7`, including version-aware capability negotiation, the standard catalog capability IDs and updated consent, fulfillment and payment shapes.
- Require the exact UCP SDK version the release was tested against (`0.0.7`) and stop configuring `ucp_sdk.version`. The SDK serves one UCP version per release and defaults to it, so an SDK release now arrives together with a plugin release instead of reaching shops on its own, and the plugin can no longer name a version its linked SDK does not serve. Version 1.2.x combined a pinned `2026-04-08` with a `>=0.0.5 <0.1.0` window: `composer update` resolved SDK 0.0.6, which no longer served that version, and the container build failed inside `assets:install` part-way through a Shopware core upgrade. `docs/ucp-version-support.md` explains what the plugin serves and what a spec bump means for a shop.
- Store the administration translations in country-agnostic files (`de.json`, `en.json`) following the current Shopware core convention; a compatibility loader keeps them working on Shopware versions before 6.7.3.
- Polish the administration texts: consistent capitalisation of the informal German address and a clearer "Total" label in the English statistics summary.

# 1.2.0

- Accept a payment payload when a checkout is completed over MCP. UCP marks `payment` as required for `checkout.complete`, but the tool declared only `id` and `dryRun`, so every call failed schema validation with `$.payment is required` and no UCP order could be placed over MCP at all. The tool now takes a payload and defaults to an empty instrument list when the agent does not send one.
- Report an applied discount as a negative `items_discount` total instead of a line item. A Shopware promotion was forwarded as an ordinary line with a negative price, which the UCP schemas reject, so every response carrying a promotion -- `discount.apply`, `cart.get`, `cart.update`, `checkout.get` and `checkout.update` -- failed its own schema and reached the agent as a server error even though the discount had been applied.
- Read the shipping address from where UCP sends it, so a checkout with separate shipping and billing addresses no longer ships to the billing one.
- Always send an absolute, openable order link in `order.permalink_url` -- for guests it is the order's deep link, which works without logging in, and it is the same link the confirmation email uses.
- Refuse a guest order read in the protocol's own vocabulary: an agent asking for someone else's guest order is told the order was not found and that the permalink is how a guest order is read, rather than receiving an internal error.
- Let an agent test a request to the UCP MCP tools before carrying it out: with `dryRun` the request is only checked and nothing is saved. A request that fails now says which field is wrong and why, instead of returning an opaque error.
- Report the code and severity of a failed agent request, and log the underlying exception, so a failure can be diagnosed from the shop's log.
- Show the Agentic Commerce tab only on sales channels that can actually sell, and fix tab, template-selection and save-button inconsistencies across Shopware 6.5, 6.6 and 6.7.
- Mark a product that has variants correctly in the OpenAI feed. `listing_has_variations` was set only when the export had variants switched on, and the variant fields were written for the parent listing as well; the flag now follows the product itself and `variant_dict` appears only on an actual variant.
- Fix the installable ZIP shipping an administration that never loaded: the packaged plugin now contains a real, compiled admin bundle that works on Shopware 6.5, 6.6 and 6.7 alike, so the Agentic Commerce tab appears after a plain upload-and-install without rebuilding anything in the shop.
- Require `ucp-php-sdk` 0.0.5 or newer, and accept every later `0.0.x` release.
